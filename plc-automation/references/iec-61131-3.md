# IEC 61131-3 Reference

## Current Standard Posture

IEC 61131-3 defines syntax and semantics for programmable controller programming languages. As of 2026-06-08, IEC 61131-3:2025 is the current IEC edition. It identifies Structured Text (ST), Ladder Diagram (LD), Function Block Diagram (FBD), Sequential Function Chart (SFC) structuring elements, configuration elements, and communication-supporting features. Older installed platforms may still implement IEC 61131-3:2013 or vendor-specific subsets.

When exact compliance matters, tell the user to verify the controller firmware, IDE version, vendor compliance statement, and project settings.

## Program Organization

- **Program Organization Units (POUs)**: Programs, function blocks, and functions.
- **Function**: No internal retained state; same inputs should produce same result.
- **Function block (FB)**: Encapsulates state; instantiate for each equipment item or reusable behavior.
- **Program**: Top-level scheduled logic, usually tied to a task or cyclic scan.
- **Configuration/resource/task**: Vendor-specific realization of runtime scheduling.

## Language Selection

- **LD**: Best for discrete maintenance-friendly interlocks, motor starter logic, permissives, seal-in circuits, and simple diagnostics.
- **ST**: Best for algorithms, arrays, loops, calculations, string/data handling, state machines, recipe logic, and compact reusable FB internals.
- **FBD**: Best for signal processing, analog control, reusable blocks, permissive/trip networks, and visual cause/effect flow.
- **SFC**: Best for explicit step/transition sequences where the platform and maintenance team accept it.

## IEC Style Rules

- Prefer explicit typed variables over implicit vendor defaults.
- Avoid hidden type conversion in safety or analog scaling logic.
- Keep scan-cycle behavior visible: timers, edge detectors, latches, and state transitions should be obvious.
- Use enumerated states where supported; otherwise use named constants.
- Bound array indexes and validate recipe/operator inputs before use.
- Document retentive variables and reset behavior.
- Treat task period changes as behavior changes for timers, pulse logic, PID, and speed calculations.

## Data Type Guidance

- Use `BOOL` for binary state and commands.
- Use signed/unsigned integer widths deliberately for counts, raw I/O, and bitfields.
- Use `REAL`/`LREAL` for engineering values where the platform supports the precision needed.
- Use `TIME` for timers and debounce periods, not integer milliseconds, unless the platform requires it.
- Prefer UDTs/structures for equipment modules: commands, permissives, trips, status, parameters, and diagnostics.

## Review Checklist

- One writer per output command.
- Trips and alarms separated from permissives.
- Reset cannot start equipment by itself.
- Auto restart behavior is explicit and site-approved.
- Loss of feedback, bad quality, and comms loss fail to a defined state.
- Timers have named constants and comments for timing basis.
- Bypasses are visible, alarmed, authorized, and not used for safety-rated functions unless formally designed.
- Simulation/test logic is isolated and cannot ship enabled accidentally.
