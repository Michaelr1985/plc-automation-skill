# Vendor File Output Standards

Use this before generating files for any PLC platform. Do not call a file "import-ready" unless it matches the vendor's documented import/export path.

## General Rule

Every generated code package must label each artifact as one of:

- **Native import**: can be imported by the vendor software using a documented import command.
- **External source**: can be added/generated by a vendor source workflow.
- **Paste-in source**: code body intended to paste into an already-created POU/routine/block.
- **Engineering reference**: design, tag list, pseudocode, or checklist, not a software import file.

If the exact vendor software version/import format is unknown, generate design plus pseudocode or paste-in source only.

## Siemens TIA Portal

Use `siemens-tia-source-standard.md`.

Correct importable targets:

- External Source `.scl` or supported STL external source with full block/type wrappers.
- SIMATIC SD `.s7dcl` for S7-1200/S7-1500 SCL/LAD/FBD blocks, DBs, and PLC data types.

Do not:

- Call loose SCL/STL snippets import-ready.
- Put STL in SIMATIC SD `.s7dcl`.
- Assume STL for S7-1200/S7-1200 G2.

## Rockwell Studio 5000 / Logix Designer

Correct importable targets:

- `.L5X` XML import/export files for routines, programs, tags, UDTs, AOIs, and other supported Logix components.
- `.L5K` text import/export for full/legacy controller exchange where appropriate.
- CSV/TXT only for supported tag/rung/comment workflows, not complete routine import unless explicitly supported by the target command.

Rules:

- Plain `.ST` files are paste-in source, not native Studio 5000 import files.
- If asked for import-ready Rockwell output, generate `.L5X` with a valid `RSLogix5000Content` root and correct component hierarchy.
- Include target Logix Designer major version and controller family assumptions.
- Do not claim an `.L5X` is verified unless it has been imported/validated in Logix Designer.

## CODESYS V3 And CODESYS-Based Runtimes

Correct importable targets:

- PLCopen XML `.xml` via `Project > Import PLCopenXML`.
- CODESYS XML `.export` where the target environment supports CODESYS native export/import.
- Full CODESYS project/archive files only when created by CODESYS tooling.

Rules:

- Plain `.ST` files are paste-in source or object-content references, not native project import files.
- PLCopen XML supports exchange of IEC 61131-3 project elements, but vendor compatibility is not guaranteed.
- CODESYS notes a PLCopenXML limitation: `VAR_GLOBAL` and `VAR_GLOBAL CONSTANT` should be separated into different variable lists.
- For WAGO, IFM, Eaton, Festo, Turck, and Raspberry Pi runtime, confirm the actual CODESYS version and device description before producing import-ready XML.

## Schneider EcoStruxure Machine Expert

Correct importable targets:

- Machine Expert XML `.export` for native exported objects.
- PLCopen XML `.xml` via `Project > Import PLCopenXML`.

Rules:

- Plain `.ST` files are paste-in source unless wrapped in a valid supported export format.
- Confirm product line: Machine Expert, Machine Expert - Basic, Machine Expert - Safety, or Control Expert. They do not share identical import formats.
- For Machine Expert Safety, do not generate safety-program import files unless the safety lifecycle and tool support are confirmed.

## Omron Sysmac Studio

Correct importable targets:

- Sysmac project files such as `.smc2`, `.csm2`, `.smc`, or `.csm` when exported by Sysmac Studio.
- IEC 61131-10 XML for supported programs, function/function-block POUs, global variables, and data types in versions that support it.
- ST project files only where the target workflow explicitly supports them, such as documented Simulink PLC Coder imports.

Rules:

- Plain `.ST` files are not generic Sysmac import-ready files.
- Confirm Sysmac Studio version, controller family, and whether IEC 61131-10 XML import is available.
- Treat safety CPU outputs separately from standard controller code.

## Delta ISPSoft / WPLSoft

Correct output depends heavily on CPU family and software version.

Rules:

- Confirm DVP/AH/AS family and whether the target is WPLSoft or ISPSoft before code syntax.
- Do not promise generic import-ready program files without a confirmed Delta export/import schema from the user's installed software.
- Safe default: provide engineering design, symbol/register tables, ladder/ST/pseudocode, memory map, and manual implementation steps.
- If the user provides an exported Delta project/source file, modify that existing format rather than inventing a schema.

## Archive ESP32 PLC / ESP-IDF

Correct output target:

- ESP-IDF native source project folder.
- Required minimum files: top-level `CMakeLists.txt`, `main/CMakeLists.txt`, `main/app_main.c`, and supporting `.c/.h` modules.

Rules:

- Archive PLC output is not IEC import/export. It is firmware source code for ESP-IDF.
- Do not generate `.ST`, `.scl`, `.L5X`, PLCopen XML, or TIA source as the primary Archive deliverable.
- Include an ESP-IDF README with target chip assumption, ESP-IDF version assumption, build command, flash command, monitor command, IO map assumptions, and hardware validation limits.
- Keep hardware IO mapping in a dedicated module or clearly separated section.
- Include fail-safe boot behavior and output de-energization on faults.
- Use NVS or another explicit ESP-IDF-supported storage method for retained step words and retained counters.
- If exact GPIO/ADC hardware is unknown, generate a clearly marked default IO map and require confirmation before field use.
- Do not claim firmware is verified without building with ESP-IDF and testing on Archive hardware.

## Output Checklist

Before finalizing generated files, state:

- Vendor and software version assumed.
- File extension and import command.
- Whether the artifact is native import, external source, paste-in source, or engineering reference.
- Required manual steps after import.
- What was not verified because the vendor IDE is unavailable.
